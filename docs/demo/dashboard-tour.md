# Grafana Dashboard Tour

The pre-provisioned dashboard **Distributed Rate Limiter Fleet** is designed to immediately convey the health, correctness, scalability, and internal behavior of the rate limiter proxy.

![Distributed Rate Limiter Fleet Dashboard](../../docs/diagrams/dashboard_screenshot_1.png)

---

## Dashboard Rows and Layout

The dashboard is split logically into 4 primary focus areas:

### 1. Traffic Overview and Health KPIs
This row answers the question: *Is the system healthy, and is it actively rate limiting?*
* **System Health Cards**:
  - **Limiter Health Status**: Displays current uptime status of the central limiter daemon.
  - **Sidecar Health Status**: Shows if sidecar proxies are active.
  - **Redis Storage Status**: Direct health check of the underlying Redis database.
* **Quota Traffic Stacked Graph**:
  - Displays Allowed (HTTP 200) vs. Rejected (HTTP 429) requests.
  - *PromQL*: `sum(rate(rate_limiter_requests_total{allowed="true"}[1m]))` and `sum(rate(rate_limiter_requests_total{allowed="false"}[1m]))`.
* **System Error Rate**:
  - Tracks non-limiter exceptions (e.g., HTTP 5xx) to monitor server failures.
  - *PromQL*: `sum(rate(routing_outcomes_total{result="error"}[1m])) / sum(rate(routing_outcomes_total[1m])) * 100`.

---

### 2. Redis and Lua Subsystem Telemetry
Since the rate-limiting calculations run as atomic Lua scripts directly on the storage node, monitoring Redis performance is crucial:
* **Lua Executions/sec**: Rate of custom script evaluations.
  - *PromQL*: `rate(redis_commands_duration_seconds_count{cmd="evalsha"}[1m])`.
* **Avg Redis Command Latency**: P50/P90/P99 latency of storage calls.
  - *PromQL*: `rate(redis_commands_duration_seconds_sum[1m]) / rate(redis_commands_duration_seconds_count[1m])`.
* **Subsystem Lua Latency (P99)**: Sub-millisecond latency tracking split by Go package targets (sliding window core, token bucket, idempotency, routing).
* **Memory Fragmentation and Connections**: Connected client sockets and memory fragmentation ratio.

---

### 3. Stripe-Style Idempotency Metrics
Idempotency is a critical concurrency feature. This dedicated section monitors the claims and cache replay outcomes:
* **Claims Rate**: Number of requests registering an idempotency token.
* **Replay Hits**: Requests served directly from the idempotency cache without hit propagation to the backend services.
  - *PromQL*: `sum(rate(idempotency_claims_total{result="replay"}[1m]))`.
* **In-Progress Conflicts (HTTP 409)**: Requests blocked because a concurrent call for the identical key is already actively executing on a worker.
  - *PromQL*: `sum(rate(idempotency_claims_total{result="in_progress"}[1m]))`.
* **Hash Mismatches**: Replays rejected because the request payload was modified since the original call.

### 4. Infrastructure and Distributed Traces
* **Go Resource Utilization**: CPU cores consumed, active Goroutines count, and GC pause durations.
* **Trace Exporter Health**: Traces generated by the sidecars and exported to Jaeger.
